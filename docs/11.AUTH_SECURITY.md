# 11. AUTH_SECURITY — Authentication, Authorization, and Security Model

## Authentication
- **Passwords:** bcryptjs, cost factor 12. Minimum 10 characters; checked against a short common-password list. Never stored or logged in plaintext.
- **Login:** email + password. On failure, same message whether the email exists or not. After 3 failed sign-ins for one email (the count covers unknown emails too, so it does not reveal accounts), each further failure doubles the wait, from 2 seconds up to 15 minutes. Waits are temporary: there is no permanent lock. The response carries `Retry-After`. A successful sign-in clears the counter. Thresholds are set with `LOGIN_BACKOFF_*` variables.
- **Sessions:** on login, the server generates 32 random bytes, sends them base64url in cookie `ss_session`, and stores only `SHA-256(token)` in `Session`. Cookie flags: `HttpOnly`, `Secure` (production), `SameSite=Lax`, `Path=/`.
- **Session TTL:** 14 days sliding with absolute cap of 30 days. Logout revokes the session.
- **Revocation:** password reset revokes all sessions; users can view and revoke individual sessions in `/app/settings/security`.
- **No tokens in localStorage or sessionStorage.** The frontend keeps only non-secret UI state.

## Email verification and password reset
- Tokens are 32 random bytes; only the hash is stored.
- Verification: expires in 24 hours. Reset: expires in 30 minutes.
- Single-use: `usedAt` is set atomically with `findOneAndUpdate({ tokenHash, usedAt: null, expiresAt: { $gt: now } })`.
- Forgot-password returns the same response for known and unknown emails.
- Reset links never contain the user ID.

## Invitations
- Owner or admin creates an invitation with role and email. Token is 32 random bytes, stored hashed, expires in 7 days, single-use.
- Accepting requires the invited email to match the signed-in user's verified email.
- Role changes and removals are audited.

## Authorization
Roles: `owner` > `admin` > `staff`.

| Capability | Owner | Admin | Staff |
|---|---|---|---|
| Org settings, billing placeholder, team roles | ✔ | ✘ | ✘ |
| Invite admin/staff | ✔ | ✔ (staff only) | ✘ |
| Services, hours, staff setup | ✔ | ✔ | ✘ |
| All appointments and customers | ✔ | ✔ | own assigned only |
| Waitlist and offers | ✔ | ✔ | view own staff's |
| Analytics and audit logs | ✔ | ✔ | ✘ |
| CSV export | ✔ | ✔ | ✘ |
| Account deletion of the org | ✔ | ✘ | ✘ |

Implementation: `requireMembership(minRole)` loads membership for `(req.user.id, req.params.orgId)`. The org ID in the URL is never trusted by itself. Nested resources use `findOne({ _id, organizationId })`, returning 404 when absent.

## Guest action tokens (booking, cancel, reschedule, slot offers)
- Generated server-side: 32 random bytes (`base64url`), stored as SHA-256 hash.
- Sent only in email links, never returned to a different browser context.
- Scoped to one appointment or one offer, with an expiry (appointment: until the appointment starts; offer: `offerExpiresAt`).
- Single-use for offer acceptance; revocable on cancellation.
- Invalid or expired token: 404 or 410 with no detail about which.

## CSRF
Cookie is `SameSite=Lax`. All mutating routes require `X-Requested-With: SlotSaver` and an `Origin` header that matches `APP_ORIGIN` or an allowlisted origin. Requests failing either check return 403.

## Rate limits
All limits are configurable through `RATE_LIMIT_*` variables (see `backend/.env.example`). They are per IP. Login backoff is per email hash, as described above. Blocked responses return `429` with `RATE_LIMITED` and a `Retry-After` header where applicable.

## Input and injection protection
- Zod validation on all bodies, queries, and params.
- `express-mongo-sanitize` strips `$` and `.` keys.
- Query operators (`$where`, `$ne`) rejected by schema validation.
- Regex search inputs are escaped.

## HTTP hardening
- `helmet` with CSP that allows only self and configured API origin.
- CORS allowlist from `APP_ORIGIN` (comma-separated). No wildcard with credentials.
- `x-powered-by` disabled. Body size limit 100 kb.

## Errors and logs
- Production error responses omit stack traces.
- Logs (pino) redact: `password`, `token`, `cookie`, `authorization`, `passwordHash`, `tokenHash`, `resetToken`, and any URL query string containing a token.
- Request IDs (`x-request-id`) are generated or passed through and returned in errors.

## Audit
See `DATABASE.md` (`AuditLog`). Entries store redacted before/after values. No API can modify or delete audit entries.

## Known limits
- No SSO, no MFA in MVP (planned: TOTP for owners).
- Rate-limit counters are kept in memory per process. With several API instances, move them to a shared store (for example Redis) before scaling out.
- Dependencies: backend and frontend audits report 0 known vulnerabilities at the time of the last check. Re-run `npm audit` before each release.
- No compliance certification has been performed.
