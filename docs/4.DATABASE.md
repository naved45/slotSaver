# 4. DATABASE — SlotSaver (MongoDB / Mongoose)

All timestamps are UTC `Date`. Every tenant-owned document has `organizationId` and `createdAt`/`updatedAt`.

_Current build note:_ the `Session`, `OneTimeToken` (and `Job` cleanup) expiry indexes are TTL indexes. They are on in production. MongoDB-compatible servers without TTL support can set `MONGO_TTL_INDEXES=off`; queries still check expiry, so correctness does not depend on TTL.

## Critical indexes (current build)
```js
// Double-booking guard. A document carries activeSlotKey ONLY while it holds the slot; the key is
// removed ($unset) on cancel, completion, or no-show. A sparse unique index ignores documents
// without the field, so cancelled slots can be rebooked. This replaces a partial-filter index,
// which not every MongoDB-compatible server supports.
Appointment.index({ activeSlotKey: 1 }, { unique: true, sparse: true });
// Offers: one live offer per slot and one per waitlist entry, same technique (activeSlotKey, activeWaitlistKey)
SlotOffer.index({ activeSlotKey: 1 }, { unique: true, sparse: true });
SlotOffer.index({ activeWaitlistKey: 1 }, { unique: true, sparse: true });
// Idempotent booking retries: idempotencyKey is stored only when provided (a null value would be
// treated as a real duplicate by a sparse unique index).
Appointment.index({ idempotencyKey: 1 }, { unique: true, sparse: true });
// Sessions and one-time tokens
Session.index({ tokenHash: 1 }, { unique: true });
OneTimeToken.index({ tokenHash: 1 }, { unique: true });
// Queue
Job.index({ idempotencyKey: 1 }, { unique: true });
Job.index({ status: 1, runAt: 1 });
// Tenancy and queries
Appointment.index({ organizationId: 1, startAt: 1 });
Appointment.index({ organizationId: 1, customerId: 1, startAt: -1 });
Customer.index({ organizationId: 1, email: 1 }, { unique: true });
WaitlistEntry.index({ organizationId: 1, serviceId: 1, status: 1 });
Notification.index({ idempotencyKey: 1 }, { unique: true });
AuditLog.index({ organizationId: 1, at: -1 });
```

Overlap: a `staffId + startAt` guard only blocks the same start instant. Overlapping but different starts are blocked by the post-write overlap check in `placeAppointment` / `rescheduleAppointment`, which rolls back the new record (status `cancelled`, `rolledBack: true`) and returns 409. Transactions are not used in this build.

## Relationships
Organization 1—N Membership N—1 User. Organization 1—N {Service, StaffProfile, Customer, Appointment, WaitlistEntry, SlotOffer, Notification, AuditLog}. Appointment N—1 Service, N—1 StaffProfile, N—1 Customer. SlotOffer N—1 WaitlistEntry.

## Deletion & retention
Account deletion anonymizes the User and removes Session and reset tokens. Appointments and audit logs are retained per the organization's retention setting (documented default: 24 months).

## Encrypted secrets
Reminder and offer emails must be sent later from a job, so their action links are stored sealed with AES-256-GCM (`ENCRYPTION_KEY`), never in plaintext. Token hashes are stored for lookup. Raw tokens are never logged or returned in responses except to the same guest on a reschedule.
