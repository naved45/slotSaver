# 3. ARCHITECTURE — SlotSaver

## Shape
Monorepo with two deployable apps:
- `frontend/` — React + Vite SPA (deployed to Vercel).
- `backend/` — Node.js + Express REST API plus a worker entry point (deployed to Render or any Node host).

External services: MongoDB Atlas (data), SMTP provider (email), optional Redis (queue backend, see below).

```
Browser ──HTTPS──▶ Vercel (React SPA)
   │  cookies (HttpOnly) + JSON
   ▼
Express API (api process)  ──▶ MongoDB (Mongoose)
   │                          ▲
   │ enqueue jobs             │ claim/run jobs
   ▼                          │
Job store (MongoDB `jobs`)  ◀─┘   (worker process)
   │ or BullMQ/Redis when REDIS_URL is set
   ▼
Email adapter (Nodemailer SMTP | dev log preview)
```

## Backend layers
`routes → controllers → services → models`, with `middleware` (auth, tenancy, rate limit, validation, errors) and `validators` (Zod) at the edge. Controllers never touch Mongoose directly. Services hold business rules (availability, booking, waitlist ranking, offers).

## Key decisions
| Decision | Choice | Why |
|---|---|---|
| Auth | Server-side sessions in `Session` collection; opaque random token in HttpOnly cookie (only SHA-256 hash stored) | Revocable, no secrets in localStorage |
| Password hashing | bcryptjs, cost 12 | Pure JS, installs without native binaries on every host |
| CSRF | SameSite=Lax cookie + Origin allowlist check + required `X-Requested-With` header on mutations | Works without extra cookie |
| Time | UTC in DB; luxon converts to organization timezone for display and rules | Correct across DST |
| Double booking | Sparse unique `activeSlotKey` (set only while the slot is held) plus a post-write overlap check that rolls back and returns 409 | Works on any MongoDB-compatible server; no transactions required |
| Slot holds | Not built. Acceptance claims the offer atomically (`pending` to `accepting`), then writes the appointment under the same slot-key guard | Simpler, with no lingering holds to clean up |
| Background jobs | Durable `jobs` collection with `idempotencyKey` unique index, `runAt`, lease (`lockedUntil`), attempts/backoff. BullMQ/Redis used when `REDIS_URL` is set | Jobs survive restarts without Redis |
| Real-time | Socket.IO on the API process, rooms per organization, optional | Dashboard refresh; app works without it |
| Email | Nodemailer adapter; without SMTP config, a dev adapter writes a preview record with status `logged_dev` | Never claims real delivery |

## Multi-tenancy
Every tenant-owned document has `organizationId`. The `tenant` middleware loads the membership for `(req.user, organizationId from route/header)`; queries are always built through a `scopedQuery(orgId, filter)` helper. Nested resources are looked up with both the resource id and `organizationId`.

## Booking flow (summary)
1. Client requests availability for service/date → server computes slots (availability engine).
2. Client submits booking with service id, staff id, start time, idempotency key.
3. Server re-runs availability for that exact slot, creates a `SlotHold` (or uses the unique index), creates the Appointment in `confirmed` state, writes status history, enqueues confirmation + reminder jobs, writes audit log.
4. Price is taken from the Service document, never from the request.

## Waitlist recovery flow
Cancellation → release slot → find candidates → rank → create `SlotOffer` (unique partial index on active offers per slot and per customer) → enqueue offer-email and expiry job → customer accepts (atomic claim) or declines/expires → next candidate.

## Deployment topology
- Vercel: frontend, `VITE_API_URL` points to the API.
- Render: web service (`npm run start`) and worker service (`npm run worker`).
- MongoDB Atlas: replica set (transactions available).
- Redis (optional): managed Redis if BullMQ is enabled.

## Current build deviations (recorded)
- No `SlotHold` model; offers and bookings use the atomic claim and slot-key guard described above.
- No MongoDB transactions. Consistency comes from single-document conditional updates and the unique guards.
- Analytics metrics are computed in code over a bounded projection (50,000 records per query). This keeps identical definitions on servers with limited `$group` support. For very large organizations, move to aggregation pipelines.
- Local tests run against FerretDB 1.24.2, a MongoDB-compatible server without TTL, partial index, or `$cond` support. Real MongoDB has not been tested in this build.
- No Socket.IO. The dashboard reloads on navigation and on demand.
